# F36 Playtesting and Balance

Canonical DESIGN-NOTES F36; delegated working foundation, not implemented software or release certification.

## Lifecycle and evidence
Prototype → probability analysis → scenario fixtures → tabletop sessions → feedback → revision → regression → release candidate → digital parity. Record rules/content version, scenario, participants anonymized, mode, setting, expected/observed result, duration, bookkeeping, agency, clue availability, resource pressure, advancement, dominant choices, issue severity and proposed fix. No human testing claimed.
## Test matrix
Cover novice/experienced groups; BP/SL/DZ native and transitional starts; occupation diversity; noncombat/combat; all presets; failure and accessibility; manual dice and digital parity; offline host/client/display. Prioritize F07 allocation, F08/F09 semantic acceptance, F10 progression, F11 timing, F12–14 injury/stress, F15 clue routes, F17–22 stock/capacity, F23–26 world and scenarios, F27–28 migration. Provisional plan at least one session per setting and representative novice/experienced coverage, repeat after material changes; not statistical proof.
## Release gates
Critical = security/data loss or unplayable core; major = material rule ambiguity/balance or blocked workflow; minor = localized issue. No unresolved critical defects; major defects resolved or explicitly accepted with documented mitigation and owner approval. Complete procedures, examples, rights, accessibility, manual fallback, versioned regression evidence. Human sessions and actual software tests are mandatory before release. Track open issues, owner, reproduction, expected/actual, fix commit, retest and status. Numerical changes require rationale and regression; no silent calibration.
